# Руководство пользователя — плагин Project Manager для Claude Cowork

[English version](USER-GUIDE.md)

**Project Manager** — AI-плагин для Claude Cowork, который автоматизирует управление IT-проектами от начала до конца. Охватывает все 32 задачи проектного управления в 6 фазах — генерирует документы, отправляет уведомления, отслеживает прогресс и координирует команду.

Специальных знаний в области программного обеспечения или AI-инструментов не требуется.

## 1. Что делает этот плагин

Управление IT-проектом означает одновременное отслеживание десятков документов, координацию команды, мониторинг дедлайнов и бюджета, контроль рисков. Это трудоёмкая работа, в которой всегда что-то рискует выпасть из внимания.

Плагин Project Manager работает как ваш AI-помощник по проектному управлению внутри Claude Cowork. Вы описываете проект обычными словами, а плагин генерирует профессиональные документы, отправляет уведомления, проверяет отклонения и ведёт вас через каждую фазу жизненного цикла проекта.

**Что автоматизирует плагин:**

- Генерацию проектных документов: уставы, планы, бюджеты, реестры рисков, протоколы, отчёты, чек-листы (34 типа документов)
- Отправку email-уведомлений стейкхолдерам и членам команды
- Мониторинг отклонений по срокам и бюджету — ежедневно и еженедельно
- Регулярный пересмотр реестра рисков по спринтам
- Координацию встреч с повестками и шаблонами протоколов
- Контроль выполнения задач и отправку напоминаний исполнителям

**Что плагин не делает:**

- Не принимает финальных решений — PM всегда проверяет и утверждает документы
- Не заменяет человеческое суждение в сложных ситуациях
- Не гарантирует результатов — он помогает, а не управляет

## 2. Основные понятия

Прежде чем начать, вот пять ключевых терминов, которые используются в этом руководстве:

**Скилл** — специализированная возможность плагина. Каждый скилл решает одну задачу: генерирует устав, составляет бюджет, отправляет напоминания и т.д. Скиллы активируются вводом названия или описанием задачи обычными словами. Всего в плагине 21 скилл.

**Слэш-команда** — сокращение, начинающееся с `/`. Команды вроде `/status`, `/init-project`, `/sprint-report` запускают конкретные действия плагина немедленно. Всего 8 команд.

**Фаза** — плагин следует 6-фазному жизненному циклу проекта: Инициация → Планирование → Прототипирование → Разработка → Запуск → Закрытие. Каждая фаза связана с определённым набором документов и задач.

**Артефакт** — любой документ, созданный плагином: устав, план, реестр рисков и т.д. Артефакты сохраняются как файлы в папке проекта.

**Уровень автономности** — насколько самостоятельно плагин действует при отправке писем. Уровень 1: отправляет автоматически. Уровень 2: отправляет, но копирует вас. Уровень 3: показывает черновик и ждёт вашего подтверждения перед отправкой.

## 3. Запуск нового проекта

### 3.1 Инициализация проекта

Откройте сессию Cowork и выполните:

```
/init-project [название-проекта]
```

**Пример:**
```
/init-project relaunch-mobilnogo-prilozheniya
```

Используйте короткое название с дефисами вместо пробелов. Рекомендуется латиница, чтобы название папки корректно работало на всех операционных системах.

**Что происходит дальше:**

Плагин создаёт следующую структуру папок в вашей рабочей директории:

```
relaunch-mobilnogo-prilozheniya/
├── CLAUDE.md                  ← Инструкции для агента (создаются автоматически, не редактировать)
├── project-state.md           ← Отслеживает, какие артефакты созданы
├── 01-initiation/             ← Документы Фазы 1
├── 02-planning/               ← Документы Фазы 2
├── 03-execution/              ← Документы Фаз 3–5
├── 04-closure/                ← Документы Фазы 6
├── meetings/                  ← Повестки и протоколы встреч
├── reports/                   ← Регламентные и периодические отчёты
├── input/                     ← Ваши исходные данные (кладите файлы сюда)
└── logs/log.md                ← Лог действий агента
```

### 3.2 Разместите исходные данные

Поместите в папку `input/` имеющиеся материалы по проекту:

- Бриф клиента или документ с требованиями
- Список членов команды с контактами
- Бюджетные ограничения или ожидания по срокам
- Любые предыдущие материалы по проекту

Плагин читает файлы из этой папки, но никогда их не изменяет.

### 3.3 Запустите Фазу 1

После завершения `/init-project` плагин автоматически предложит начать Фазу 1. Подтвердите, написав «да» или «начнём», или сразу переходите к первому скиллу.

## 4. Фаза 1 — Инициация

**Цель фазы:** понять проект, определить скоуп, выявить стейкхолдеров и утвердить первые документы.

**Документы Фазы 1:**
- Устав проекта
- Карта стейкхолдеров
- Предварительная оценка (сроки + бюджет)
- Опросник клиента (опционально)

---

### 4.1 Отправить опросник клиенту

Если нужно собрать структурированную информацию от клиента до начала работ — используйте этот скилл первым.

**Как активировать:**

```
Создай опросник для клиента по проекту реланч мобильного приложения
```

или просто:

```
Нужно отправить клиенту опросник
```

**Что спросит плагин:**
- Название проекта и имя клиента
- Тип опросника: бриф клиента или ретроспектива команды?
- Специфические темы для включения (опционально)

**Что вы получите:**

Заполненный документ-опросник (`client-questionnaire.md`) в папке `01-initiation/`. Можно отправить клиенту напрямую или скопировать в письмо.

---

### 4.2 Сформировать устав проекта

Устав — основополагающий документ проекта. Он определяет цель, скоуп, команду, бюджет, сроки и критерии успеха. Всё начинается с него.

**Как активировать:**

```
Создай устав проекта
```

**Что спросит плагин:**

- Название и описание проекта (что создаёте?)
- Имя клиента или спонсора
- Ключевая цель — что нужно достичь и к какому сроку?
- Скоуп: что входит, что явно исключено?
- Команда: ключевые роли и ответственные
- Бюджет (примерный диапазон)
- Основные ограничения или уже известные риски

**Совет:** можете вставить сюда текст из ответов клиента на опросник — плагин автоматически извлечёт нужные данные.

**Что вы получите:**

Файл `project-charter.md` в папке `01-initiation/`. Плагин покажет краткое резюме и запросит ваше подтверждение. После утверждения отметит устав как завершённый в `project-state.md` и разблокирует зависимые задачи.

---

### 4.3 Построить карту стейкхолдеров

Карта стейкхолдеров определяет всех, кто имеет интерес к проекту, — их роли, уровень влияния и формат коммуникации.

**Как активировать:**

```
Построй карту стейкхолдеров
```

**Что спросит плагин:**

- Список участников: имена, роли, организации
- Для каждого: уровень влияния (Высокий / Средний / Низкий) и заинтересованность в проекте
- Предпочтительный формат получения обновлений (письма, встречи, отчёты)

**Что вы получите:**

Файл `stakeholder-map.md` с матрицей влияния/интереса и рекомендуемым подходом к коммуникации для каждой группы стейкхолдеров.

---

### 4.4 Создать предварительную оценку

До составления полного плана получите приблизительную оценку сроков и бюджета на основе устава.

**Как активировать:**

```
Создай предварительную оценку проекта
```

**Что спросит плагин:**

- Тип проекта (новый продукт, редизайн, интеграция, внутренний инструмент?)
- Состав команды и приблизительный размер
- Известные дедлайны или бюджетные ограничения

**Что вы получите:**

Файл `estimate.xlsx` с диапазонами сроков и бюджета (оптимистичный / реалистичный / пессимистичный), плюс краткая методологическая заметка с объяснением расчётов.

---

## 5. Фаза 2 — Планирование

**Цель:** создать детальный, исполнимый план проекта. Все документы Фазы 2 зависят от утверждённого устава.

**Документы Фазы 2:**
- План проекта (WBS, вехи, расписание Ганта)
- Детальный бюджет
- План распределения ресурсов
- Реестр рисков
- План коммуникаций

---

### 5.1 Сгенерировать план проекта

**Как активировать:**

```
Создай план проекта
```

**Что спросит плагин:**

- Подтверждение, что устав утверждён (или вставьте ключевые детали, если нет)
- Список фаз или основных этапов
- Ключевые вехи и целевые даты
- Доступность членов команды (полная / частичная занятость)

**Что вы получите:**

Файл `project-plan.md` с WBS (иерархический список задач и результатов), вехами и расписанием Ганта в текстовом формате. В плане используется система нумерации `WP-XXX` — любой документ может ссылаться на конкретные задачи по ID.

> Утверждение плана проекта разблокирует Реестр рисков и План коммуникаций.

---

### 5.2 Сгенерировать детальный бюджет

**Как активировать:**

```
Создай бюджет проекта
```

**Что спросит плагин:**

- Роли в команде и их ставки (почасовые или ежемесячные)
- Длительность участия каждой роли в каждой фазе
- Дополнительные статьи расходов: лицензии на ПО, инфраструктура, подрядчики, резерв

**Что вы получите:**

Файл `project-budget.xlsx` с разбивкой затрат по фазам, итогами и строкой резерва на непредвиденное. Бюджет связан с ID задач WP из плана проекта.

---

### 5.3 Создать план распределения ресурсов

**Как активировать:**

```
Создай план ресурсов
```

**Что спросит плагин:**

- Список членов команды с ролями
- Какие фазы проекта каждый из них участвует
- Процент загрузки по фазам (например, 50% в Фазе 2, 80% в Фазе 4)

**Что вы получите:**

Файл `resource-plan.md` с наглядной таблицей распределения — кто над чем работает, когда и с какой загрузкой. Выделяются потенциальные перегрузки или пробелы в покрытии.

---

### 5.4 Сформировать реестр рисков

Реестр рисков — живой документ: создаётся здесь в Фазе 2 и обновляется на протяжении всего проекта.

**Как активировать:**

```
Создай реестр рисков
```

**Что спросит плагин (режим Фазы 2):**

- Риски, которые вы уже видите: технические, организационные, бизнесовые, внешние
- Для каждого риска: вероятность (Низкая / Средняя / Высокая) и потенциальный ущерб

**Что вы получите:**

Файл `risk-register.md` с каждым риском, оценённым по шкале вероятность × ущерб, уровнем риска (Низкий / Средний / Высокий / Критический) и предложенным планом митигации. Реестр будет обновляться автоматически по регламентной задаче `risk-update` в активных фазах.

---

### 5.5 Сформировать план коммуникаций

**Как активировать:**

```
Создай план коммуникаций
```

Плагин автоматически считает карту стейкхолдеров (если она создана). Если карты нет — запросит данные о стейкхолдерах.

**Что вы получите:**

Файл `comm-plan.md` с матрицей коммуникаций: кто получает какую информацию, в каком формате, как часто и кто за это отвечает. Включает путь эскалации для проблем и решений.

## 6. Фаза 3 — Прототипирование

**Цель:** оценить варианты решений, выбрать лучший подход и получить одобрение на продолжение.

**Документы Фазы 3:**
- Таблица сравнения прототипов
- Протокол встречи (Go/No-Go)
- Письмо об утверждении

---

### 6.1 Сравнить варианты прототипов

Когда у вас 2–4 варианта подхода или решения, используйте этот скилл для системной оценки.

**Как активировать:**

```
Сравни варианты прототипов
```

**Что спросит плагин:**

- Количество вариантов для сравнения (от 2 до 4)
- Краткое описание каждого варианта
- Критерии оценки (плагин предлагает стандартный набор: техническая реализуемость, качество UX, стоимость, сроки, риски — можно настроить)
- Веса критериев (или использовать значения по умолчанию)

**Что вы получите:**

Файл `comparison-table.xlsx` с взвешенной матрицей оценки, итогами по каждому варианту и рекомендацией. Финальный выбор остаётся за вами.

---

### 6.2 Оформить протокол встречи

Используйте этот скилл после любой проектной встречи для создания структурированного протокола из ваших заметок.

**Как активировать:**

```
Оформи протокол встречи
```

**Что спросит плагин:**

- Дата встречи, тип и список участников
- Принятые решения (вставьте черновые заметки — плагин структурирует их)
- Задачи: кто что делает и к какому сроку

**Что вы получите:**

Файл `meeting-protocol-YYYY-MM-DD.md` в папке `meetings/`. Решения и задачи связываются с ID задач WP из плана проекта, где это применимо.

---

### 6.3 Сформировать письмо об утверждении

Используйте этот скилл для запроса формального одобрения от клиента или спонсора перед переходом к следующей фазе.

**Как активировать:**

```
Создай письмо об утверждении Фазы 3
```

**Что вы получите:**

Документ `approval-letter.md`, готовый к отправке, плюс шаблон `email-approval.md` для Gmail. Письмо содержит краткое резюме того, что утверждается, и чёткий призыв к действию.

## 7. Фаза 4 — Разработка

**Цель:** исполнение плана проекта через спринты разработки. Мониторинг прогресса, управление изменениями, поддержание плана в актуальном состоянии.

**Ключевые скиллы Фазы 4:**
- Отчёты о прогрессе спринта
- Проверки отклонений по срокам и бюджету
- Анализ влияния изменений скоупа

---

### 7.1 Запустить отчёт по спринту

**Как активировать:**

```
/sprint-report
```

или

```
Создай отчёт о прогрессе спринта
```

**Что спросит плагин:**

- Номер и даты спринта
- Выполненные задачи (вставьте из Jira или опишите обычным текстом)
- Задачи в работе и заблокированные
- Проблемы или решения, которые нужны

**Что вы получите:**

Файл `sprint-report-SXX.md` в папке `reports/`. Включает сравнение выполненного с запланированным, сводку по блокерам и рекомендуемые действия.

> Если подключён Jira MCP, плагин автоматически подтянет статусы задач — вам останется только подтвердить или скорректировать.

---

### 7.2 Проверить отклонения

**Как активировать:**

```
/deviation-check
```

Плагин сравнивает текущий прогресс с планом проекта и бюджетом. Фиксирует:
- Задачи с отставанием (на сколько дней)
- Бюджетные статьи с перерасходом или под угрозой
- Риски, которые материализовались

**Что вы получите:**

Файл `deviation-report-YYYY-MM-DD.md` в папке `reports/`. Если отклонения превышают пороги, плагин подготовит черновик уведомления для стейкхолдеров на ваш просмотр.

---

### 7.3 Оценить запрос на изменение скоупа

Когда клиент или стейкхолдер просит изменить скоуп проекта — сначала оцените влияние с помощью этого скилла.

**Как активировать:**

```
Оцени запрос на изменение: добавить интеграцию с соцсетями в мобильное приложение
```

**Что спросит плагин:**

- Описание запрашиваемого изменения
- Кто запросил и зачем
- Предварительная оценка сложности

**Что вы получите:**

Файл `change-impact-CR-XXX.xlsx` с анализом влияния по трём измерениям: отклонение по срокам, отклонение по бюджету, уровень риска. Плагин оценивает изменение как Низкое / Среднее / Высокое по влиянию и рекомендует одобрить, отложить или отклонить. Финальное решение — за вами.

## 8. Фаза 5 — Запуск

**Цель:** подготовить и провести запуск проекта. Координировать параллельные потоки работ и иметь готовый план реагирования на инциденты.

**Документы Фазы 5:**
- Чек-лист готовности к запуску
- Чек-лист технической готовности
- Чек-лист передачи в эксплуатацию
- План реагирования на инциденты
- Отчёт о синхронизации потоков

---

### 8.1 Сформировать чек-листы

**Как активировать:**

```
Создай чек-лист готовности к запуску
```

или

```
Создай чек-лист технической готовности
```

или

```
Создай чек-лист передачи в эксплуатацию
```

Плагин предзаполнит каждый чек-лист стандартными пунктами из шаблона PMBoK и обогатит данными из вашего плана проекта. Вы проверяете и финализируете перед использованием.

**Что вы получите:**

- `launch-checklist.md` — все условия для проверки перед запуском
- `tech-readiness-checklist.md` — технические и инфраструктурные проверки
- `handover-checklist.md` — шаги для передачи проекта в эксплуатацию

---

### 8.2 Создать план реагирования на инциденты

Готовьтесь до запуска, а не после того как что-то сломается.

**Как активировать:**

```
Создай план реагирования на инциденты
```

**Что спросит плагин:**

- Наиболее вероятные типы инцидентов для вашего проекта (технический сбой, ошибка деплоя, PR-кризис и т.д.)
- Ключевые люди, ответственные за реагирование
- Путь эскалации

**Что вы получите:**

Файл `response-plan-INC.md` с уровнями серьёзности (Критический / Высокий / Средний / Низкий), процедурами для каждого типа инцидента, планом коммуникаций и задачами постинцидентного анализа.

---

### 8.3 Синхронизация потоков работ

Когда во время запуска параллельно идут несколько потоков работ — используйте эту команду для проверки согласованности.

**Как активировать:**

```
/sync-check
```

**Что вы получите:**

Файл `sync-report-YYYY-MM-DD.md` со статусом каждого потока работ, зависимостями между ними, блокерами и критическими элементами, требующими немедленного внимания.

## 9. Фаза 6 — Закрытие проекта

**Цель:** формально закрыть проект. Документировать произошедшее, зафиксировать уроки и передать результаты.

**Документы Фазы 6:**
- Отчёт план/факт
- Отчёт о закрытии проекта

---

### 9.1 Сформировать отчёт план/факт

**Как активировать:**

```
Создай отчёт план/факт
```

**Что спросит плагин:**

- Плановые и фактические сроки (дата начала, дата окончания, даты вех)
- Плановый и фактический бюджет (по статьям)
- Плановый и фактический скоуп (какие фичи были сделаны, какие перенесены)

**Что вы получите:**

Файл `plan-fact-report.md` с таблицами отклонений по всем трём измерениям и краткими комментариями к каждому значимому расхождению.

---

### 9.2 Сформировать отчёт о закрытии проекта

Отчёт о закрытии агрегирует всё: устав, отчёт план/факт, реализованные риски и уроки, извлечённые из проекта.

**Как активировать:**

```
Создай отчёт о закрытии проекта
```

Плагин автоматически считает все доступные артефакты проекта. Вас попросят добавить раздел «Уроки» своими словами.

**Что вы получите:**

Файл `closure-report.md` — комплексный документ, пригодный для архивирования и передачи спонсорам или будущим командам проектов.

## 10. Справочник по командам

Слэш-команды — это быстрые сокращения для частых действий. Вводятся в начале сообщения.

### `/init-project [название]`

Инициализирует новый проект. Создаёт структуру папок, `CLAUDE.md`, `project-state.md` и запускает Фазу 1.

**Пример:** `/init-project crm-upgrade`

---

### `/status`

Показывает текущее состояние активного проекта: фаза, созданные артефакты, следующие рекомендуемые шаги. Используйте в начале каждой сессии для ориентации.

**Пример:** `/status`

---

### `/next-step`

Рекомендует одно следующее действие на основе того, что уже сделано и какие зависимости выполнены. Полезна, когда неясно, что делать дальше.

**Пример:** `/next-step`

---

### `/sprint-report`

Генерирует отчёт о прогрессе спринта. Плагин запрашивает данные текущего спринта или подтягивает их из Jira (если подключён).

**Пример:** `/sprint-report`

---

### `/deviation-check`

Проверяет отклонения по срокам и бюджету относительно плана. Фиксирует проблемы и готовит оповещения при превышении порогов.

**Пример:** `/deviation-check`

---

### `/risk-update`

Проводит ревью реестра рисков: спрашивает о новых рисках, о выполненных планах митигации, обновляет оценки рисков.

**Пример:** `/risk-update`

---

### `/sync-check`

Синхронизирует параллельные потоки работ во время Фазы 5. Показывает статус всех потоков и критические зависимости.

**Пример:** `/sync-check`

---

### `/remind-executors`

Отправляет напоминания членам команды с просроченными задачами. Плагин читает план проекта, определяет просроченные задачи и готовит письма-напоминания.

**Пример:** `/remind-executors`

---

## 11. Email-уведомления

Плагин может отправлять письма от вашего имени через Gmail (если подключён). Все письма используют трёхуровневую систему автономности — вы выбираете, сколько контроля хотите сохранить.

### Уровни автономности

**Уровень 1 — Автоматически:** плагин отправляет письмо сразу. Используется для рутинных, низкорисковых уведомлений (например, еженедельные статус-отчёты команде).

**Уровень 2 — Автоотправка с копией PM:** плагин отправляет письмо и ставит вас в копию. Используется для оповещений об отклонениях и напоминаний исполнителям.

**Уровень 3 — Черновик на согласование:** плагин создаёт черновик и показывает его вам до отправки. Вы проверяете, редактируете при необходимости и подтверждаете. Используется для запросов на утверждение, отчётов стейкхолдерам и любых писем клиентам.

### Как изменить уровень автономности

Когда скилл предлагает отправить письмо, он сообщит уровень по умолчанию. Чтобы изменить его, напишите:

```
Используй уровень автономности 3 для этого письма
```

или

```
Не отправляй автоматически — покажи мне черновик
```

### Если Gmail не подключён

Плагин создаёт файл `.md` с содержимым черновика письма. Вы можете скопировать текст и отправить вручную из своего почтового клиента.

## 12. Автоматические регламентные проверки

Плагин может выполнять рутинные проверки автоматически по расписанию. Они настраиваются при `/init-project` и становятся активными в Фазах 3–5.

| Задача | Расписание | Цель |
|--------|------------|------|
| Еженедельный статус-отчёт | Каждый понедельник в 9:00 | Сводка прогресса проекта для стейкхолдеров |
| Ежедневная проверка отклонений | Пн–Пт в 9:00 | Выявление проблем со сроками и бюджетом до эскалации |
| Ревью реестра рисков | Каждый понедельник (по спринтам) | Обновление оценок рисков исходя из текущего состояния |
| Синхронизация потоков | Каждый понедельник в 9:00 (только Фаза 5) | Проверка согласованности параллельных потоков |
| Напоминания исполнителям | Пн–Пт в 10:00 | Отправка напоминаний по просроченным задачам |

Все регламентные задачи можно запускать вручную в любой момент с помощью слэш-команд.

**Чтобы приостановить регламентную задачу:**

```
Приостанови ежедневную проверку отклонений
```

**Чтобы возобновить:**

```
Возобнови ежедневную проверку отклонений
```

## 13. Работа без внешних интеграций

Плагин полностью функционален без Jira, Gmail и Google Calendar. Вот что меняется в файловом режиме:

| Функция | С интеграциями | Без интеграций |
|---------|----------------|----------------|
| Отчёты по спринту | Подтягивает задачи из Jira автоматически | Вы вводите данные по задачам в чате |
| Проверки отклонений | Читает статусы из Jira автоматически | Вы подтверждаете текущий статус вручную |
| Email-уведомления | Отправляет через Gmail | Сохраняет черновик в `.md` для ручной отправки |
| Планирование встреч | Создаёт событие в Calendar автоматически | Предоставляет данные события для ручного создания |

Для большинства пользователей файловый режим полностью достаточен. Добавьте интеграции позже, когда захотите большей автоматизации.

## 14. Советы для лучших результатов

**Начинайте каждую сессию с `/status`**
Плагин продолжает с того места, где вы остановились. Запуск `/status` в начале показывает текущее состояние и предотвращает случайное дублирование работы.

**Кладите исходные данные в `input/` до запуска скиллов**
Чем больше контекста у плагина, тем лучше результат. Заполненный опросник или бриф в папке `input/` даёт больше, чем ответы на вопросы по одному в чате.

**Проверяйте и утверждайте перед тем, как двигаться дальше**
Каждый скилл запрашивает ваше одобрение перед тем, как отметить артефакт завершённым. Потратьте минуту на чтение результата — поправки на этом этапе гораздо проще, чем после генерации зависимых документов.

**Используйте `/next-step` когда неясно, что делать**
Вместо того чтобы гадать, спросите плагин. Он знает карту зависимостей и предложит правильное действие исходя из того, что уже сделано.

**Ведите по одной сессии на фазу**
Длинные сессии с множеством переключений контекста иногда могут вызвать у плагина путаницу с тем, какой проект активен. Начало новой сессии для каждой крупной фазы поддерживает порядок.

**Описывайте задачи обычными словами**
Не нужно знать название скилла. «Нужно проверить, не отстаём ли мы от графика» или «помоги подготовиться к демо для клиента» — достаточно, плагин сам определит подходящий скилл.

## 15. Часто задаваемые вопросы

**В: Плагин может вести несколько проектов одновременно?**

О: Да. У каждого проекта своя папка и файл `CLAUDE.md`. В начале сессии скажите плагину, над каким проектом работаете: «Переключись на проект mobile-app». Плагин прочитает соответствующий `CLAUDE.md` и активирует контекст этого проекта.

---

**В: Я случайно запустил `/init-project` дважды. Теперь есть дублирующиеся папки. Что делать?**

О: Удалите дублирующую папку вручную (оставьте ту, где есть нужный контент). Затем запустите `/status`, чтобы убедиться, что плагин читает правильную папку.

---

**В: Плагин сгенерировал документ, но я внёс в него правки вручную. Он перезапишет мои изменения?**

О: Нет. Плагин только создаёт новые файлы — он никогда не перезаписывает уже существующие файлы в папке проекта. Если нужно перегенерировать документ (например, обновить его после изменения плана), скажите плагину явно: «Перегенерируй реестр рисков на основе обновлённого плана проекта».

---

**В: Можно использовать плагин без запуска `/init-project`?**

О: Отдельные скиллы (например, генерация устава или протокола встречи) можно использовать без инициализации полного проекта. Однако скиллы, зависящие от других артефактов (например, план коммуникаций требует карты стейкхолдеров), работают лучше всего внутри правильно инициализированного проекта.

---

**В: Что делать, если плагин сгенерировал документ, который мне не нравится?**

О: Скажите, что именно нужно изменить: «В реестре рисков не хватает риска зависимости от вендора — добавь, пожалуйста». или «Перепиши раздел скоупа в уставе — список исключений слишком расплывчатый». Плагин обновит конкретный раздел без перегенерации всего документа.

---

**В: Плагин хранит данные моих проектов на внешних серверах?**

О: Нет. Все файлы проектов хранятся локально на вашем компьютере в папке, выбранной при настройке. Плагин работает полностью внутри Claude Cowork на вашей машине. MCP-интеграции (Jira, Gmail, Calendar) подключаются к этим внешним сервисам напрямую — промежуточного хранения нет.

---

**В: Регламентные задачи не запускаются. Почему?**

О: Регламентные задачи работают только пока открыто десктопное приложение Claude. Если приложение закрыто, задачи запустятся в следующее расписанное время после открытия приложения. Проверьте, что задачи включены, запустив `/status`.

---

**В: Можно использовать плагин на английском?**

О: Да. Плагин автоматически определяет ваш язык по вводу и отвечает на том же языке. Все 21 скилл и 8 команд поддерживают английский и русский языки. Переключаться между языками можно в любой момент в рамках одной сессии.

---

## 16. Глоссарий

**Артефакт** — документ, созданный плагином и сохранённый в папке проекта (устав, план, реестр рисков и т.д.).

**Уровень автономности** — насколько самостоятельно плагин действует для конкретного действия. Уровень 1: полностью автоматически. Уровень 3: требует вашего одобрения перед продолжением.

**Команда** — сокращение, начинающееся с `/`, запускающее конкретное действие плагина.

**MCP (Model Context Protocol)** — стандарт, позволяющий плагинам Claude подключаться к внешним сервисам: Jira, Gmail, Google Calendar.

**Отклонение** — измеримое расхождение между плановым и фактическим состоянием проекта (отставание по срокам, перерасход бюджета).

**Диаграмма Ганта** — временная визуализация, показывающая когда задачи начинаются и заканчиваются; в плагине представлена в текстовом формате.

**PMBoK** — Project Management Body of Knowledge. Международный стандарт проектного управления, издаваемый PMI. Плагин основан на гибриде PMBoK 8 + Agile.

**plan-fact report (отчёт план/факт)** — сравнение того, что было запланировано, с тем, что фактически произошло: по срокам, бюджету и скоупу.

**project-state.md** — внутренний реестр плагина для всех созданных артефактов и их статуса утверждения.

**Реестр рисков** — структурированный список идентифицированных рисков с оценкой вероятности, ущерба и планами митигации.

**Скилл** — специализированная возможность плагина, решающая одну конкретную задачу (например, генерация устава, проверка отклонений).

**Стейкхолдер** — любой, кто имеет интерес в проекте: клиент, спонсор, члены команды, конечные пользователи.

**Фаза** — один из шести этапов жизненного цикла проекта: Инициация, Планирование, Прототипирование, Разработка, Запуск, Закрытие.

**WBS (Work Breakdown Structure, иерархическая структура работ)** — иерархическая декомпозиция всех результатов и задач проекта на управляемые компоненты.

**WP-XXX** — система нумерации задач, используемая во всех проектных документах для связи связанных элементов.
